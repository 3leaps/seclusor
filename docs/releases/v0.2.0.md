# Release Notes — v0.2.0

**Release Date**: August 3, 2026
**Status**: Encrypted document operations and asset signing

## Overview

Seclusor v0.2.0 is the release where encrypted secrets documents become
first-class day-to-day surfaces—not just storage formats you decrypt to edit.

Operators can inspect, validate, mutate, and rekey bundle and inline documents
without a plaintext-on-disk editing step. Release and distribution workflows
gain detached asset signatures with fail-closed verification. Published CLI and
Go artifacts build from locked, audited dependency graphs.

This release also introduces optional recipient metadata (schema v1.1.0) so
write and rekey behavior stays stable across team workflows. That metadata has
a deliberate fail-closed compatibility boundary for older strict readers—see
[Upgrade Notes](#upgrade-notes).

## Who this is for

- **Operators / DevSecOps** maintaining encrypted secrets in CI or shared
  repos, who want in-place mutation and clear rekey semantics
- **Release engineers** who need signed distribution assets with expected-key
  verification
- **Go integrators** who need to _load_ encrypted documents (read path); full
  encrypting mutation and asset-signing envelopes remain CLI/Rust in this cut

## Highlights

### Encrypted read workflows

`secrets get`, `list`, `validate`, `export-env`, and `run` automatically detect
plaintext JSON, inline-encrypted JSON, and bundle ciphertext. Identity files
can be selected directly or discovered by public key without loading unrelated
private key material.

Validation reports whether it completed a full cryptographic validation or a
structural-only validation. Shell export keeps values on stdout and diagnostics
on stderr, requires an allow pattern, and refuses interactive-terminal output
unless explicitly forced.

### Encrypted write and rekey workflows

`secrets set`, `unset`, `import-env`, and `rekey` now operate on encrypted
documents:

- Bundle writes decrypt in memory, mutate, and atomically replace the encrypted
  document.
- Inline writes preserve untouched ciphertext and encrypt only changed values.
- Inline `unset` and description-only edits can be structural-only and require
  no identity.
- `secrets rekey` is the single command for changing recipient membership.
- `secrets init --codec bundle` creates an empty encrypted bundle at a new path
  when explicit recipients are supplied.

Prefer `--value-stdin`, `--value-file`, or `--value-env` for secret input.
Legacy `--value` remains available but warns because command arguments may be
visible in shell history or process listings.

### Asset signing

The new `seclusor assets sign` and `seclusor assets verify` commands create and
verify detached `seclusor.signature.v1` JSON envelopes:

- assets are hashed with streaming SHA-256;
- signing keys contain Ed25519 seeds encrypted at rest with age;
- verification requires an expected public key or fingerprint by default;
- strict envelope parsing rejects unknown, duplicate, null, or malformed data.

`--trust-embedded-key` checks self-consistency only. It does not establish that
the embedded key is one the verifier already trusts. The signed `claimed_at`
field is operator metadata, not trusted timestamp evidence.

### Published artifact integrity

The CLI, Go static libraries, and private TypeScript-native build surface now
use committed lockfiles and locked build entrypoints. CI audits both Rust
dependency graphs, checks crypto-component parity across surfaces, and runs
negative controls so stale locks and graph divergence fail closed.

## Upgrade notes

### What you should do

1. **Upgrade writers and readers together** if any document will carry
   top-level `recipients` metadata (schema v1.1.0).
2. Prefer **non-argv value channels** (`--value-stdin` / `--value-file` /
   `--value-env`) for new automation.
3. Use **`secrets rekey`** whenever recipient membership changes—do not expect
   ordinary `set` / `import-env` to rewrite the recipient set.
4. For release assets, verify with an **expected public key or fingerprint**;
   do not treat `--trust-embedded-key` as a trust root.

Documents that never establish `recipients` remain readable on older binaries.

### Schema v1.1.0 recipient metadata

Encrypted write workflows can add a top-level `recipients` field and update
`schema_version` to `1.1.0`. When `recipients` is present in JSON-at-rest,
direct plaintext credential values are rejected; references and
`sec:age:v1:` ciphertext values remain valid.

Older binaries that predate `recipients` and use strict unknown-field handling
**fail closed** when opening those documents (safe direction). Upgrade every
writer and reader that must use documents carrying recipient metadata.

### Recipient changes

Use `secrets rekey` to add or remove recipients. Ordinary `set` and
`import-env` operations preserve the established recipient set and refuse
ambiguous recipient changes.

### Go and TypeScript surfaces

The Go binding adds read-side loaders for encrypted bundle and inline
documents. Encrypted mutation and asset-signing envelope APIs remain Rust/CLI
surfaces in this release. The TypeScript package remains private and does not
publish platform addons as part of v0.2.0.

## Security and operational notes

Honest residuals operators should know about:

- Identity files require owner-only mode and current-user ownership on Unix.
- Asset verification fails closed unless an expected key or fingerprint is
  supplied, or embedded-key trust is explicitly requested.
- Bundle writes use authenticated outer encryption. Inline recipient metadata is
  plaintext structure and relies on repository integrity controls (not age
  authentication of that field).
- Matching recipient _counts_ do not prove identical recipient membership—a
  same-count membership swap is not detected by count checks alone.
- Imported environment values may remain in ordinary owned strings until
  dropped; a zeroizing value type remains future hardening.
- Upstream age identity objects do not zeroize the secret scalar on drop, so
  identity lifetimes should remain narrow.
- Data-passphrase write workflows are not included; encrypted document writes
  use X25519 recipients.
- Unix creates use owner-only permissions. Windows fresh-file ACL parity and
  crash-atomic replacement guarantees remain platform limitations.

See [App Note 04](../appnotes/04-encrypted-write-operations.md) for the command
matrix and complete residual table.

## Distribution

### Release assets

- Linux amd64 and arm64
- macOS arm64
- Windows amd64 and arm64

Each release includes SHA-256 and SHA-512 checksum manifests. Detached
signatures and exported verification keys are attached after local signing and
verification.

### Package managers

Homebrew and Scoop manifests are updated **after** the GitHub release is
published (same flow as prior cuts):

```bash
# Homebrew
brew install 3leaps/tap/seclusor
# or, once already installed:
brew update && brew upgrade seclusor

# Scoop
scoop bucket add 3leaps https://github.com/3leaps/scoop-bucket
scoop install seclusor
# or:
scoop update seclusor
```
