# Release Notes — v0.2.1

**Release Date**: August 11, 2026  
**Status**: Security patch (child-environment boundary + recipient-set guard)

## Overview

Seclusor v0.2.1 is a **security patch** for teams already on the v0.2.0
encrypted-document surface. Install it if you use `secrets run` with a
passphrase environment variable, or if you rotate identities against a durable
recipients list.

It closes a privilege-boundary defect in `secrets run` (the named passphrase
variable no longer reaches the child) and hardens write paths so a stale
recipients list cannot silently restore a retired recipient after identity
rotation.

The only new flags are deliberate and narrow: `rekey --write-recipients` for an
explicit list refresh, and `--allow-recipient-mismatch` when you intend to
change the recipient set.

A GitHub Security Advisory is published with this release. See the repository
**Security Advisories** page for machine-readable affected ranges, severity,
and CVE status (CVE request is scoped to the `secrets run` item).

## Who this is for

- **Operators** using `secrets run` with passphrase-protected identities via
  `--passphrase-env`
- **Teams rotating identities** against encrypted stores that keep a durable
  `recipients.txt` (or equivalent) for writes
- **Integrators** who shell out to the CLI (library-only crypto/keyring
  consumers are not affected by the `secrets run` issue)

## Security summary

### 1. `secrets run` and the child environment

**What was wrong.** `secrets run` launched the child with the ambient process
environment intact and layered injected store keys on top. The variable named
by `--passphrase-env` was therefore inherited by the child and by every process
it spawned. `--allow` / `--deny` filter **which store keys are injected**; they
do not filter ambient environment pass-through.

**What 0.2.1 does.** Child-environment construction goes through a single
chokepoint that requires the excluded variable name to be declared. The command
also refuses to start if any effective child environment **value** equals the
resolved passphrase (covering aliases under a different variable name).

**Affected versions.** **v0.1.4 – v0.2.0** inclusive — the exposure requires both
`secrets run` (present since earlier releases) and the `--passphrase-env`
channel (since v0.1.4).

**Not affected (this issue only).** Consumers that link cryptography or keyring
crates as libraries, without invoking the CLI `run` command, are not affected by
this item.

**Residual.** When the passphrase is supplied via `--passphrase-env`, it remains
present in the **parent** `seclusor` process environment for the lifetime of
that invocation (and in the shell that exported it). On Linux, a same-user
observer can read it from `/proc/<pid>/environ`; equivalent inspection exists on
other platforms. **This fix does not make `--passphrase-env` equivalent to
`--passphrase-file` or `--passphrase-stdin`.** Prefer those channels for
ordinary use; scope the variable to a single command and unset it immediately
afterwards.

**Narrow recovery exception.** On v0.2.1 and later, an identity created from a
CRLF-terminated passphrase file on v0.2.1 or earlier can be unlocked by
supplying its exact legacy value, including the retained carriage return,
through `--passphrase-env`. Use that access only to generate a replacement
identity with normalized file or stdin input, rekey encrypted data to the
replacement recipient, retire the legacy identity, and unset the variable. Do
not use this environment recovery workflow with `secrets run` on v0.2.0 or
earlier.

**Workaround on unpatched binaries** (`printf` is a shell builtin, so the value
never appears in process arguments):

```bash
printf '%s' "$VAR" | env -u VAR \
  seclusor secrets run --passphrase-stdin … -- <command>
```

### 2. Recipient-set divergence after rotation

**What was wrong.** Rotating an identity did not update an external recipients
file, and write paths did not report the divergence. A subsequent write using a
stale list could re-encrypt the store to a retired recipient and report success.
Removing an old identity file locally is not revocation while the store remains
encrypted to that recipient.

**What 0.2.1 does.**

- Write paths with recipient metadata (`set`, `import-env`, `rekey`, bundle
  encrypt) compare the write-target set to recorded metadata and **fail closed**
  on divergence, printing each public key as `+age1…` / `-age1…`. The signal is
  a set difference the operator must read — not a claim that seclusor classifies
  “re-grant” vs intentional membership change.
- Intentional membership changes require **`--allow-recipient-mismatch`** on the
  same command. That flag covers only the recipient-set check that just failed;
  it is not a general force switch and does not suppress other validation or
  cryptographic failures.
- **`rekey --write-recipients PATH`** optionally writes the canonical resulting
  public-key set to a named path after a successful rekey (atomic public-data
  write). It never rewrites `--recipient-file` unless the same path is also
  named with `--write-recipients`. Encrypted rekey and recipient-list refresh are
  not one transaction: if the list write fails after the encrypted output
  commits, retry the refresh against that committed output with an identity able
  to open the new recipient set.

**Affected versions.** Reported trap: **v0.2.0** only (`rekey` first shipped
there). Underlying missing cross-check: **v0.1.0 – v0.2.0** for writes that
accept a recipient set, though the delta is only **detectable** once schema
**v1.1.0** `recipients` metadata exists (v0.2.0+).

**Residual (schema).** On legacy **v1.0.0** documents there is no recorded
recipient set to compare. The comparison is **indeterminate**. Seclusor prints
an explicit notice and establishes metadata from the write target only when the
operation covers every inline encrypted field or writes a bundle; a partial
inline write instead refuses and directs you to `secrets rekey`. It does not
infer recipient identities from age X25519 stanzas. Fail-closed divergence
applies only when metadata is present.

**Library note.** Library consumers performing their own document writes gain a
comparison predicate in 0.2.1, but policy enforcement lives in the CLI. Do not
read the “not affected” line for the `secrets run` item as covering this issue.

### If you may have been exposed

1. **Upgrade to 0.2.1 first.**
2. **Then rotate the affected identity.** On 0.2.1, recipient divergence fails
   closed. Rewrite durable recipient sources (or pass `--write-recipients`
   during rekey) **before any further encrypted write**.
3. Treat any credential the exposed process could reach as compromised, not only
   those it was given.

## Upgrade notes

1. Install **v0.2.1** from the GitHub release, Homebrew tap, or Scoop bucket.
2. Prefer **`--passphrase-file`** or **`--passphrase-stdin`** for automation that
   does not need an environment variable. If you keep `--passphrase-env`,
   treat the parent-process residual above as part of that choice. Use its
   exact-byte behavior only for the narrow legacy CRLF recovery described above.
3. After any identity rotation:
   - rekey to the new recipient set;
   - refresh durable recipient lists with `--write-recipients` (or rewrite them
     by hand and verify age1 strings);
   - only then run further `set` / `import-env` writes.
4. When a write fails closed with a recipient delta, read the `+`/`-` lines
   first — then repeat with `--allow-recipient-mismatch` only if the change is
   intentional.
5. Prefer documents that already carry schema v1.1.0 `recipients` metadata so
   the divergence guard can fail closed. On v1.0.0 documents, a full rewrite
   emits the indeterminate establishment notice; a partial inline write refuses
   and requires `secrets rekey` first.

## Highlights (non-security packaging)

- Release uploads include the PGP public key (`release-key.asc`) with provenance
  selection.
- CI retains generated SBOM artifacts under stable package-named CycloneDX
  filenames for audit trails.

## Compatibility

- Document schema is unchanged from v0.2.0 (schema v1.1.0 with optional
  `recipients` metadata).
- CLI: new optional flags only (`--write-recipients`,
  `--allow-recipient-mismatch`). Workflows that already kept the write-target
  recipient set aligned with document metadata continue to work.
- **Intentional behavior change:** writes that previously **succeeded** while
  the write-target recipient set diverged from recorded metadata now **fail
  closed** when that metadata is present. That is the security fix, not a
  regression — resolve the `+`/`-` lines or pass `--allow-recipient-mismatch`
  only for deliberate membership changes.
- Go and TypeScript binding **API contracts** are unchanged; bump package
  versions to 0.2.1 for lockstep release numbering. The `secrets run` fix is a
  CLI concern.
